# Problem: Harness fixes for long tasks

GOAL: Find which changes to the harness, not the model, raise the pass rate of the coding agent on long tasks (40 or more tool calls), and by how much. Long tasks pass 31 percent of the time against 78 percent for short ones, and the same task often passes on one run and fails on the next. The team wants a ranked list of harness changes, each with a predicted effect on long-task pass rate and its cost, the failure kind it addresses, the mechanism, and a test. The answer should also say honestly which failures cannot be fixed without a model change. Today only a retry from scratch is kept, and it lifts the pair of runs to 44 percent but doubles the cost of a failed task. Situation: An LLM coding agent with read_file, edit_file, run_shell and search tools runs on an internal suite of 120 repository tasks, 48 of them long. One person read 40 failed long runs by hand and sorted them into six failure kinds. Three changes were tried: raising the step cap to 100, retrying once from scratch, and summarising every 20 steps. Only the retry was kept. The folder holds the taxonomy notes, the harness description, the measurement plan, the tried-changes list, literature notes (ReAct, Reflexion, SWE-agent, Lost in the Middle, tau-bench), open questions, and a 30-run sample CSV that is synthetic, not real data. Scope: In: harness changes (prompt, tools, context handling, memory, retries, step cap, verification) judged on the 48 long tasks of the 120-task suite; out: any change to the model, fine-tuning, or a bigger model. Open questions: Does pinning the task text alone remove most 'lost the goal' failures, or do those runs drift for another reason?; Is a loop best broken by a rule (same command twice with the same output means stop and rethink) or by asking for a prediction first?; Should verification be a harness step the agent cannot skip, and what does it cost in runs that would have passed anyway?; Is a notes file better than a summary, given that summaries dropped the task text?; Which changes combine and which cancel out (for example, notes file plus pinning plus summaries)?; Which failures are the model's limit, where no harness change helps (guess: part of gave up early and tool misuse)? PURPOSE: Find the best answer to: Harness fixes for long tasks.

BASELINE: none, and there is no objective score. Each proposal is read blind by a panel of 3 judges, each scoring it from 1 to 10 on the criteria below without seeing the other proposals. People's opinions count at a bounded weight. The best proposal so far is the reference.

CRITERIA:
- Ranked list: The answer gives harness changes in ranked order, each with a predicted long-task pass-rate gain and a token cost per run.
- Failure link: Each change names the failure kind from the 40-run taxonomy it targets and the mechanism by which it helps, tied to counts or observations in the files.
- Testable: Each change has a test that fits the measurement plan: 48 long tasks, seeds 1-3, with pass rate, pass^3, tokens, and failure kinds.
- Keep rule: Predicted results are judged against the keep rule: at least +6 points on long tasks, cost rise at most 20 percent, no drop on short tasks.
- Model limits: The answer separates failures a harness change can fix from those that likely need a better model, with reasons.
- Fits budget: The proposed study order (cheap screen on 12 tasks, then full 48) stays within about 2,500 runs and about 15 full measurements.

FORM OF A PROPOSAL:
A proposal in markdown with exactly these five sections, in this order: CLAIM, FROM THE FACTS TO THE IDEA, FROM THE IDEA TO THE RESULT, WEAK POINTS, PROPOSED TEST. It cites at least one known fact by its id (for example [F1]). It describes something that can be done for: Harness fixes for long tasks.

KNOWN FACTS (cite at least one by its id):
[F1] Short tasks (under 15 tool calls) pass 78 percent; tasks over 40 tool calls pass 31 percent; the same task can pass and fail on different runs. (source: problem_brief.md, opening paragraph)
[F2] Baseline long tasks: pass 31 percent, pass^3 12 percent, 65k tokens per run. Short tasks: pass 78 percent, pass^3 61 percent, 14k tokens per run. (source: measurement_plan.md, Baseline numbers)
[F3] Of 40 failed long runs read by hand: lost the goal 11, loop 9, stale context 7, wrong verification 6, gave up early 4, tool misuse 3. (source: failure_taxonomy_notes.md, table)
[F4] In 9 of 11 'lost the goal' runs the task text was no longer in the context window; the harness trims oldest messages first and the task text is the oldest. (source: failure_taxonomy_notes.md, Observations)
[F5] The 9 loop runs averaged 2,400 tokens per cycle, and the agent never stated what it expected the fix to change. (source: failure_taxonomy_notes.md, Observations)
[F6] All stale context runs involved files longer than 300 lines that the agent had read in full once. (source: failure_taxonomy_notes.md, Observations)
[F7] A person reading only the summary would have accepted 5 of the 6 wrong-verification runs. (source: failure_taxonomy_notes.md, Observations)
[F8] Passing and failing runs used the same tools in the first 10 steps; the difference shows after step 25. (source: failure_taxonomy_notes.md, Observations)
[F9] Harness: system prompt of about 900 tokens, four tools, step cap of 60 tool calls, 128k window; when over 100k, oldest messages are dropped until under 80k. (source: harness_today.md)
[F10] No memory between runs, no notes file, no checkpoint; a failed run is retried from scratch at most once; verification is left to the agent and nothing checks it. (source: harness_today.md)
[F11] Cost per long task today is about 65k tokens per run, 2 runs with the retry. (source: harness_today.md)
[F12] Raising the step cap from 60 to 100 moved long-task pass from 31 to 33 percent and cost per task up 45 percent; loop runs just looped longer. Not kept. (source: what_we_tried.md, change 1)
[F13] Retry from scratch with a different seed raised the pair's long-task pass rate from 31 to 44 percent and doubles cost of a failed task. Kept. (source: what_we_tried.md, change 2)
[F14] Summarising every 20 steps moved pass from 31 to 34 percent; stale context failures fell but lost-the-goal failures rose; in 6 of 10 read summaries the task text was shortened or dropped. Not kept. (source: what_we_tried.md, change 3)
[F15] Untried: pinned task text, prediction before re-running a test, re-reading a file after editing, harness-run verification, scratch notes file. (source: what_we_tried.md, What nobody has tried)
[F16] Suite is 120 repository tasks, 48 long, with hidden tests run after the agent stops. (source: measurement_plan.md, first paragraph)
[F17] Measurement per change: pass rate over seeds 1, 2, 3 (144 runs), pass^3, tokens and wall time per run, and failure kinds on a 20-run sample. (source: measurement_plan.md, list)
[F18] A change is kept if long-task pass rises 6 points or more (seed spread about 4 points), cost per task rises at most 20 percent, and short-task pass does not fall. (source: measurement_plan.md, keep rule)
[F19] Study budget is 2,500 runs, about 15 full changes, with screening on a 12-task subset first. (source: measurement_plan.md, Budget)
[F20] ReAct names drifting reasoning and repeated actions as main failure kinds; Reflexion's written reflection after a failure is cheap to add to the retry. (source: reading_notes_agents.md, ReAct and Reflexion)
[F21] SWE-agent: a windowed file viewer, syntax-checked edits and short tool outputs raised solve rate; long noisy tool results fill the context. (source: reading_notes_agents.md, SWE-agent)
[F22] Lost in the Middle: models use the start and end of the context better than the middle; the task text sits at the start until it is trimmed away. (source: reading_notes_agents.md, Lost in the Middle)

HARD CONSTRAINTS:
C1. A proposal has the five sections CLAIM, FROM THE FACTS TO THE IDEA, FROM THE IDEA TO THE RESULT, WEAK POINTS and PROPOSED TEST, and cites at least one known fact by its id.
C2. The model is fixed: no fine-tuning, no retraining, no bigger model.
C3. Allowed changes are the system prompt, tools and tool descriptions, context trimming or summarising, memory between steps, retries and checkpoints, step cap, and how the agent is told to verify.
C4. Every change must be measurable on the 120-task suite with the same seeds.
C5. A change that doubles cost per task is out, even if it passes more.
C6. Keep rule: long-task pass up 6 points or more, cost up at most 20 percent, short-task pass not lower.
C7. Study budget is 2,500 runs in total, about 15 full measurements, with a 12-task screen first.
C8. The agent must not see or change the hidden tests.
C9. The trajectories CSV is synthetic and must not be treated as real evidence.
C10. There is no objective score: proposals are ranked by a blind panel on ranked list, failure link, testable, keep rule, model limits, fits budget, with people's opinions at a bounded weight.
